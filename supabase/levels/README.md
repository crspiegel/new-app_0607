# 레벨 키 이름 바꾸기 (A, 2026-10-29) — 운영 반영 순서

옛 내부 키 `Level 1`~`Level 4`(옛 Level 1 = Beginner)를 화면 표기와 같은 새 키로 바꾼다.

| 옛 키   | 새 키      | 화면 표기 |
| ------- | ---------- | --------- |
| Level 1 | `beginner` | Beginner  |
| Level 2 | `level-1`  | Level 1   |
| Level 3 | `level-2`  | Level 2   |
| Level 4 | `level-3`  | Level 3   |

대상 표는 둘이다: `content_pages`, `page_backgrounds`. 운영 DB에는 **사용자가 Supabase SQL Editor에서 직접** 실행한다.
열기: Supabase 대시보드 → 프로젝트 → **SQL Editor** → **New query** → 파일 내용 전체 붙여넣기 → **Run**.

| 순서 | 누가   | 무엇                                                             | 기대 결과                                                                                                                            |
| ---- | ------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 0    | PM     | **A 코드 푸시(운영 반영)를 먼저 끝낸다**                         | 운영 사이트가 새 주소(`#months/beginner`)로 열리고 내용이 그대로 보임(옛 키를 호환으로 읽는 중)                                      |
| 1    | 사용자 | `00-precheck.sql` 실행 (읽기 전용)                               | 표 1개. note가 `old → …` 또는 `new`. **`UNKNOWN`이 있으면 멈추고 작업자에게 표를 붙여넣기**                                          |
| 2    | 사용자 | `01-rename.sql` 실행                                             | 표 1개(table·level·before·after). 옛 키 줄은 모두 `after = 0`, 새 키 줄의 `after` = 해당 옛 키 `before`(+이미 새 키로 저장된 페이지) |
| 3    | 사용자 | `00-precheck.sql` 다시 실행                                      | 모든 줄 note = `new`, 행 수 합계 = 2번의 after 합계                                                                                  |
| 4    | 사용자 | 운영 사이트에서 Beginner·Level 1~3 페이지, 학생 QR 1개 열어 보기 | 내용·표지·배경이 1~2번 전과 같음                                                                                                     |

## 지켜야 할 것

- **0번(코드 푸시) 전에 1·2번을 하지 않는다.** 옛 코드는 새 키를 못 읽어 사이트·학생 페이지가 빈 화면이 된다.
- 2번은 한 트랜잭션이다. 오류가 나면 아무것도 바뀌지 않으니 오류 문구를 그대로 작업자에게 붙여넣는다. 다시 실행해도
  안전하다(두 번째 실행은 옮길 행이 없어 before = after).
- 2번 끝에 CHECK 제약이 걸려 이후 옛 키·오타 저장은 오류가 난다(조용히 잘못 저장되는 것보다 낫다).
- 같은 페이지가 옛 키와 새 키로 둘 다 있으면(코드 푸시 후 관리자가 그 페이지를 저장한 경우) **새 키 행이 이기고 옛 행은
  지운다** — 00의 note에 `(N already saved as …: old copy dropped)`로 미리 보인다.
- 이 SQL은 `migration.sql`에 넣지 않았다(일회성 데이터 이동). CHECK를 `migration.sql`에 합치고 코드의 옛 키 호환 읽기를
  지우는 일은 SQL 2(Phase 3.5) 백로그다.

## 파일

- `00-precheck.sql` — 읽기 전용 현황(표·레벨별 행 수, 옮길 키, 지울 낡은 사본).
- `01-rename.sql` — 이름 바꾸기 + CHECK + 실행 전/후 행 수 표.
- 로컬 검증: `npm.cmd run test:sql` (PGlite, 운영 접속 없음) — `tests/levels-sql.spec.js`.
